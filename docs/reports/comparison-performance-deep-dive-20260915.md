# 比对任务性能的进一步深度分析

日期：2026-09-15。范围：当前实际工作区；在前一轮缓存优化和冗余清理之后继续找收益。此次交付为分析、隔离实验和可复核证据；业务代码、配置、历史任务和 Golden 真值未修改，未部署。

## 结论

**仍有值得实施的优化。优先做页面拆并判断提前、匹配计算复用，然后做识别结果复用和识别服务调度。** 前两项已经在隔离实验中证明能减少计算，同时保持所验证的输出一致。它们不需要关闭语义匹配、缩减候选或者降低 OCR 质量。

但本地优化不能独自完成 90 秒目标：已有真实长合同执行约 172 秒，OCR 阶段约 97 秒。扫描件 PP-Structure 请求仍是最长路径；只有缩短这条路径，或在重复任务中直接复用有效识别结果，才可能实现更大的端到端收益。

本报告区分三类证据：本次组件实验、此前真实外部调用、尚未实施的设计推断。组件收益不能直接作为完整任务提速比例，也没有将多次实验的提升百分比相加。

## 2. 第一优先：先判定拆并页是否成立，再算组合相似度

位置：[page_alignment.py](../../backend/app/services/page_alignment.py) 的 `_dynamic_alignment()`、`_group_supported()`。

现在每个动态规划位置都尝试普通匹配、合页、拆页。合页和拆页会提前计算组合页的完整相似度；进入 `_group_supported()` 后又先算组合分数，之后才用单页分数否决组合。大量最终不允许的组合，因此仍支付了长文本 `SequenceMatcher` 的成本。

隔离原型只改变纯计算的执行顺序：

1. 先保留原有空白日期、单页稳定性、最低分数和文字覆盖判断。
2. 有任一否决条件就返回，不构造和比较组合页。
3. 全部必要条件通过，才计算组合分数，并继续使用原有阈值和 DP 转移。

没有删除 DP 状态、收窄搜索范围、改变分数公式或取消拆并页。拆页方向的相似度保持原方向；`SequenceMatcher` 的左右参数不能随意互换。

长合同相似度实际计算次数从 **14,685 降到 6,152**，减少 **58.1%**。优化前 profile 的主要热点是文本匹配，不是 DP 数组和回溯，因此先重写 DP 存储的收益会很有限。

两种长度均交替执行三轮，以下为中位数：

| 样本 | 当前实现 | 判断提前 | 减少 | 对齐输出 |
|---|---:|---:|---:|---|
| 55＋54 页 | 13.849 s | 5.934 s | 57.2% | 三轮全部一致 |
| 22＋22 页 | 1.144 s | 0.582 s | 49.2% | 三轮全部一致 |

另对 **17 组**保存的准备后文档验证，覆盖单侧 **3–55 页，17/17 页面结果全部一致**。全量结果见下方记录。

实施时应继续使用单次调用的缓存，保留小页、空白页、插删页和连续拆并页的回归。完整下游结果与并发内存仍需正式验收；组件输出相同不等于已经重跑完整 Golden。

证据：[实验源代码](../../output/analysis/performance-deep-dive-20260915/alignment_probe.py)、[计时与计算次数](../../output/analysis/performance-deep-dive-20260915/alignment-results.json)、[全量页面组件对照](../../output/analysis/performance-deep-dive-20260915/alignment-corpus.json)。

## 3. 第二优先：把匹配中的重复计算补齐

位置：[providers.py](../../backend/app/services/matching/providers.py)、[candidate_scoring.py](../../backend/app/services/matching/candidate_scoring.py)、[matcher.py](../../backend/app/services/matcher.py)。

已有的 `MATCH_FEATURE_CACHE_ENABLED` 并没有覆盖全部高频特征。此次 profile 发现三个明确缺口：

- **向量长度反复求和。** `_cosine_score()` 每比较一对条款，都重新计算左右两个向量的长度。同一向量参与很多次召回和候选评分；同一对向量还会在 `top_k()` 和 `score()` 中重复计算。初轮长合同原型的 profile 记录了 107,827 次余弦计算。
- **条款路径反复解析。** 37,903 个候选导致约 76,536 次 `_canonical_path()` 调用、211,509 次路径项处理，而输入仅 730 条条款。现有缓存覆盖了编号、部分正文和业务字段，未缓存整个路径。
- **同一页关系反复扫描。** 每个候选都重新构造页集合并遍历对齐结果。页面关系的种类明显少于条款候选对，可在本次匹配中按页集合复用。

隔离原型依次复用向量长度、已算的有向向量对分数、页集合关系，再加条款路径。保持全部候选、全部模型请求、原有浮点求和顺序、舍入和分配逻辑。

兼容环境下，长合同两次当前 / 两次候选交替对照，中位数 **14.809 → 6.535 秒，减少 55.9%**。当前范围 14.680–14.937 秒，候选范围 6.449–6.621 秒。

每次仍执行 **390 次模型响应回放（23 embedding＋367 rerank）**，HTTP 失败 0、缓存缺失 0，候选数量相同，完整 `ClausePair` 结果一致。本次没有重新调用模型，数字描述的是固定模型响应下的组件耗时；不能把历史真实匹配的 23 秒直接替换成 6 秒。

初轮 Python 3.13 环境的分步实验还显示，向量/页关系复用先带来 13.49 → 9.02 秒，再增加路径复用后为另一组 13.34 → 6.17 秒；这些初轮数值仅用于判断热点，最终计时采用上面的兼容环境。

正式实现不能直接照搬探索用无上限字典。当前长合同原型保存 408 个向量长度、83,622 个向量对分数和 1,676 个页关系；需要单次匹配的生命周期、容量预算、淘汰与结束释放。缓存键应采用明确的条款/向量索引及输入版本，不能把临时 Python 对象地址作为跨任务键。

后续可以探索批量矩阵运算，但应单独验证浮点误差、阈值附近的候选顺序和分配。先完成保持原运算顺序的复用，收益已经足够明显。

证据：[初轮分步缓存实验](../../output/analysis/performance-deep-dive-20260915/matching_probe.py)、[含路径复用实验](../../output/analysis/performance-deep-dive-20260915/matching_path_probe.py)、[详细结果](../../output/analysis/performance-deep-dive-20260915/matching-path-results.json)。

### 为什么此时不优先减少重排次数

历史长合同匹配阶段约 23 秒，其中 embedding 批次等待约 2.47 秒、rerank 批次等待约 5.66 秒；二者之外仍有大量本地计算。367 组重排的 HTTP 耗时累加约 44.61 秒，但它们并发执行，不能当成可直接节省的 44.61 秒。

位置召回贡献了 36,885 个候选来源标记，总候选 37,903 个，说明宽位置窗口值得后续研究。但它覆盖真实跨页和移位条款，缩窄会改变决策，应在等价复用完成后独立验证。不能由这些来源计数推导“这些候选全部多余”。

## 4. 重复任务的最大机会：复用识别结果

对 `storage/tasks/*/input/*/*.pdf` 按文件内容 SHA-256 去重，本次发现 **120 个输入文件，40 个不同文件**，存在 80 次重复文件出现。

这证明本地数据中存在复用机会，但目录包含反复测试，**不是生产请求样本，不能宣布生产命中率为 66.7%**。需要从正常业务任务中另测原版重复率、新版重复率、双侧同时命中率，以及按 OCR 成本加权的命中率。

建议首先实现文档级 OCR 成功结果缓存：

- 缓存键包含 PDF 内容哈希、服务/模型版本、影响识别的全部选项和结果格式版本。
- 分别保存 PP-OCRv5 与 PP-Structure 的成功响应；恢复时验证页完整性和结构，再进行当前版本的转换、融合与后处理。
- 缓存原始识别结果或不可变识别文档，不缓存被另一份合同影响的准备后文档、条款配对、差异或人工审核状态。
- 每次命中生成任务自身的文档对象和文件/证据路径，避免后续原地修改污染其他任务；同文件同时请求可合并为一次在途识别。
- 有界磁盘容量、版本失效、主动强制重识别入口；缺页、失败、降级响应不能当成合格缓存。

收益取决于最长路径是否命中。长合同原版识别约 54.52 秒、新版约 96.56 秒，二者已经并发：**只缓存原版，不能直接宣称完整任务节省 54 秒**。双侧有效命中才能大幅缩短识别阶段；首次上传的全新扫描件仍需服务侧优化。

这一缓存也有失败恢复价值：例如 PP-Structure 失败时，保留已经成功的另一识别分支，可以减少再次发起任务时的重复工作。必须保留原任务失败记录，新任务重新验证复用条件。

证据：[文件去重清单](../../output/analysis/performance-deep-dive-20260915/python313-exploration/input-reuse.json)、[活动提取流程](../../backend/app/services/extractors/ppstructure_ocr_hybrid.py)。

## 5. 首次任务与多人使用：改造 OCR 调度

### 5.1 先解决最长服务路径

历史长合同四路请求同时开始，其中扫描件 PP-Structure HTTP 约 **95.78 秒**，扫描件 PP-OCRv5 约 **56.65 秒**。原版和新版已并行，每份内部也已并行，因此“再把两份文件并行起来”不是新方案。

下一步应与 OCR 服务侧联合定位：按请求记录接收时间、排队、PDF 解码、页面预处理、各模型推理、序列化、页数、重试与内存。当前客户端的一个 `http_request` 无法判断 95 秒到底花在哪一步。

确认后才选择页批次、服务内部批处理、共享预处理/检测、模型加速等方案。初始实验可比较少量有界页批次，而不是一次发起所有页面请求；必须验证页号、坐标、缺页检测、阅读顺序、表格和印章输出。不能假设现有 API 已支持服务器端页范围。

页面级原生识别在前轮引入页眉和 `ISO/IS0` 新差异，仍保持关闭。取消第二路 OCR 会改变文字与版面证据来源，不能作为默认性能开关直接打开。

### 5.2 调度应改善短任务延迟

`_parallel_extraction_slots` 是进程级信号量，上限目前为 2，限制的是整份混合识别文档，而不是分别限制两种 OCR 服务。

在已有双任务并发记录中，短合同原版等槽约 **49.49 秒**，新版等槽约 **90.80 秒**。短合同从提交到结束约 156 秒，独立执行约 50 秒。这个差距主要需要调度和资源竞争分析，不能归因于差异算法。

建议独立评估：文档/页批次的公平队列、短任务优先但带等待补偿、两种服务各自的并发预算、有限批次释放槽位。先保持总资源约束进行实验，再根据服务容量提高预算。只增加 task worker 数，会增加等待中的任务和内存，未必增加成功吞吐。

首份文档完成后提前执行真正单文档的准备工作，也值得研究；但 `prepare_pair()` 包含双侧互相校验和修改，不能把整个准备阶段直接并行搬到 OCR 内部。

证据：[并发任务记录](../../output/analysis/compare-performance/final/candidate-concurrent/summary.json)、[槽位实现](../../backend/app/services/pipeline_stages.py)、[队列实现](../../backend/app/infrastructure/task_runner.py)。

## 6. 文档准备和视觉阶段

本次保存真实 `DocumentPreparationStage` 的入口文档，再单独 profile：约 **11.39 秒中，`recover_ruled_tables()` 占 8.69 秒，52 次 `HoughLinesP()` 直线检测占 7.15 秒**。这比文字提取、格式化和简单规则处理更值得继续研究。以上是嵌套计时，不能相加。

还实际测试了把既有表单排除、字符完整性检查移到整页渲染/检测之前：两次当前、两次原型，完整准备后文档和 503 条处理决策一致，但 **Hough 调用仍为 52 次，准备阶段中位数 10.89 → 11.07 秒**。因此该候选不推荐作为本样本的性能改造；这点负波动也不足以宣布稳定退化。

下一轮视觉优化应聚焦直线检测本身，而不是继续堆像素缓存。当前检测用 0.1° 的角度步长寻找直线，再只保留接近水平的 ±4° 线段用于偏斜估计。可独立试验更有针对性的偏斜估计、原生矢量线读取、局部网格检测和结果复用。不过这些方案可能改变纠偏与单元格归属，**尚无本次收益或等价性证明**，需覆盖微旋转、断线、浅线、签署表单和续页表格。

证据：[真实入口 profile](../../output/analysis/performance-deep-dive-20260915/preparation-profile.txt)、[判断提前的否定结果](../../output/analysis/performance-deep-dive-20260915/table-gate-results.json)、[表格恢复实现](../../backend/app/services/ruled_table_recovery.py)。

此前页面像素缓存并未显著降低矩阵图形组件的渲染次数，继续单纯扩大 64 MiB 缓存不是优先方案。可以进一步记录相同页面、参数、裁剪区域的重复访问，优先共享实际重复的检测结果或改善页面访问顺序。

视觉处理有不同缩放、颜色空间、批注开关和裁剪范围；不同参数不能硬合并。所有页面遍历和低对比度检测都有识别目的，直接跳过“看起来没有变化的页”会影响签章、手写和二维码差异。

### 已排除的微优化

初轮环境对四份参考 PDF 的 `get_text('rawdict')` 做了三轮实验。关闭图片提取后文字行、字符和坐标完全相同，但本次样本总耗时本身很小，变化主要是毫秒级。提前筛选 `.txt` 修复候选同样没有秒级收益。因此它们可随代码维护顺手改，不应包装成主要性能方案。

PyMuPDF 官方确实指出，不需要图片时可关闭 `TEXT_PRESERVE_IMAGES`；这是一条适用建议，具体收益仍须实测。[官方性能说明](https://pymupdf.readthedocs.io/en/latest/app1.html#performance)。另外，通用 `PyMuPDFExtractor` 当前用原始块序号生成 `block_id`，去掉图像块可能改变文本块编号，不能不经验证全局替换。

## 7. 影响性能判断的正确性与环境问题

**重排超长失败要单独处理。** 前轮存在 2,048 token 上限错误，当前 provider 会对异常重试，之后关闭整个 matcher 的后续重排。并发组收到失败的时机会影响哪些条款还能使用重排，造成不稳定的降级输出。应按实际 tokenizer 控制 query＋候选输入长度，区分不可重试的输入错误和瞬时故障，并记录每组是否完成正式模型路径。不能把失败后少调用模型的更短时间当成性能进步。

**锁定基准环境。** 本仓库存在两个本地环境：`backend/.venv` 为 Python 3.13.5、OpenCV 5.0.0，根目录 `.venv` 为 Python 3.12.8、OpenCV 4.13.0。实际探针中前者的 `HoughLinesP()` 返回 `(N,4)`，后者返回 `(N,1,4)`，而当前表格代码按后一种形状解包，前者会报错。本次没有修改依赖或兼容逻辑；主要计时已在根目录环境重新验证，初轮探索单独保存。使用未锁定的依赖版本时，不应横向混算性能。

**内存计时口径要修正理解。** `StageMetrics.memory_mb_start/end` 调用的是进程历史峰值，不是每个阶段结束时的存活内存。多次任务后数值不下降不能直接证明泄漏。后续应同时测当前 RSS、阶段峰值、任务结束后的存活对象，以及缓存的实际保留字节。

**质量门禁仍有既有失败。** 前轮完整 Golden 有 55 条失败，本次没有修复这些问题，也没有重新执行外部 OCR Golden。组件等价实验只能支持对应优化继续实施，不能据此声称整体质量门禁通过。

## 8. 建议实施顺序与验收

| 顺序 | 内容 | 验收重点 |
|---|---|---|
| 1 | 页面对齐中的纯否决条件提前 | 所有页面对应、状态、分数、锚点一致；完整流程与双任务内存验证 |
| 2 | 向量长度/有向分数、条款路径、页关系复用 | 候选与模型请求保持一致；边界分数、完整匹配和差异对象一致；缓存有界 |
| 3 | 文档 OCR 成功结果复用与请求合并 | 命中与强制重算对照；配置失效、缺页、跨任务修改、取消与失败恢复 |
| 4 | OCR 服务追踪、批次与公平调度 | 首次与重复任务分别统计；长短混合任务的成功吞吐、排队时间、P50/P95、失败率和峰值内存 |
| 5 | 探索表格直线检测热点；当前判断提前原型不进入实施 | 独立实验，修复决策、正文、坐标、表格结构和差异结果逐项验证 |
| 6 | 候选收窄、页面原生路由、减少模型路径 | 独立实验开关，真实变化和证据逐项审核，先解决已有质量问题 |

本地等价优化的验收应先做固定 OCR 和固定模型响应的完整质量对照，再做相同服务条件下交替的真实长短任务。超过两三个样本的尾延迟和并发容量，需要单独的代表性工作负载；本次不给 P95 或稳定端到端提速承诺。
