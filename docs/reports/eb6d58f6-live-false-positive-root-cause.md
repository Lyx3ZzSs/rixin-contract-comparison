## 二、为什么只部分生效

`compare_service.py` 在模块级导入 `pipeline_stages.py`；后者在模块级导入 `DocumentPreparer`、`NativeHeadingRepairService`、`SigningFieldValueOCR` 和 `WholePageSigningVisualRecall`。这些类随已加载的模块留在进程中，再次 import 不会刷新其实现。

部分工具在函数内部才导入，例如 `table_slash_recovery`、`blank_evidence.reject_stamp_text_as_person`。如果首次调用发生在文件修改之后，它们可能加载新实现，而调用它们的主流程仍是旧实现。新任务的表现与此一致：

| 分支 | 实际任务记录 | 含义 |
|---|---|---|
| 第 17 页斜杠 | 有 `7 → /` 修复记录 | 新的局部斜杠恢复已经执行 |
| 第 28 页续表 | 无 `visible_native_continuation_grid` 恢复记录，仍报新增 4 | 旧主流程没有调用新增的续表恢复 |

| 联系人 | 已拒绝红章字“中”，但无设计方 `MISSING_FIELD_LOCAL_OCR` 恢复 | 过滤更新了，后续恢复仍是旧逻辑 |

这也解释了联系人为何从“错报中”变成“不输出实际姓名”：旧恢复逻辑只寻找缺少的字段键；被清空的 contact 元素仍存在，不被视为缺少。新实现额外处理 `rejected_stamp_value`，但实际任务没有运行这一分支。

## 五、新进程仍未解决的内容和展示问题

**D024 的“邮箱：147399”仍然是截断读数。** 原图买方邮箱行有更长填写，当前结果只保留前段。元素同时记录 `content_recognition_status=CONFIRMED / SINGLE_SOURCE` 和 `observation_state=UNOBSERVED / CROSS_COLUMN_EVIDENCE_REJECTED`。邮箱行消失有真实结构依据，但“完整邮箱值就是 147399”不成立。

根因链：

1. `extractor.py` 的 `_fuse_field_value_evidence` 接受单一局部 OCR 片段；额外复核主要覆盖签名、日期，没有验证邮箱完整性。
2. `comparator.py` 因另一来源的多行污染把 observation 降为 UNOBSERVED，但 content status 独立计算，仍可保留 CONFIRMED。
3. `diff_builder.py` 使用既有文字生成差异；前端继续展示文字、增删方向及笼统的复核提示。

因此“识别到一段文字”“完整字段值已确认”“字段确实发生变化”尚未形成统一的约束。这个问题在当前修复版本仍存在，不能靠重启解决。

地址、邮箱空模板的删除以及“代表（签字）”标签新增，也应与实际填写值变化区别对待。例如 D027 是卖方空签字栏的模板变化；D031 对应设计方有墨迹却被章遮挡的签字区域。它们不能一概删除，也不能让用户将“新增代表（签字）：”理解成已经可靠识别一个新增姓名。当前展示主要突出增删方向，提示没有充分说明变化对象与不确定原因。

## 六、上一轮验收缺口与后续顺序

上一轮验证证明了新进程下的已知修复，却未验证正在服务页面的 API 进程加载了同一版本。保留其余历史变化是防止漏报的检查，不能证明剩余内容全部正确。新任务暴露了这两个边界。

应先统一服务运行版本，再做实际 API 验收，避免继续对旧模块的结果叠加算法补丁：

1. 排空活动任务并完整重启后端；通过正常上传 API 创建新任务，检查相同 4 条误报、3 处纠错及联系人恢复。
2. 保存启动版本/代码摘要及任务执行版本；健康检查应能说明当前运行版本。目前 `/health` 只返回 `status: ok`，无法验证修复是否加载。
3. 对邮箱等不完整读数、污染证据、模板结构变化和填写值变化统一状态及展示规则，增加覆盖整个任务的内容审核。

当前没有重启服务，实际历史任务仍是 35 条底层差异、34 个展示事件；32/31 是本轮隔离回放结果。
