## 根因链条与代码证据

### 1. D040：表格去重把 OCR 字符完全一致当作必要条件

这是证据最完整的一条链：

1. `document_understanding.json` 中两侧 `p25_ppocrv5_b3` 均为 table，均包含 `芯片组：1ntel 7500 芯片组`。
2. 原文 native 提取结果为 `芯片组:lntel 7500 芯片组`，其中小写 l 与 OCR 数字 1 不同。
3. `native_heading_repair.json` 明确记录 `inserted / p25_native_section_title_1 / missing_ocr_section_title`。
4. `clauses_original.json` 的 OC142 引用了这个补入块；对应 NC142 没有该块。OC142 页集合为 24、25、27，NC142 为 24、27。
5. 最终 D040 比较正文字符串，把仅原文额外拥有的表格副本报告为删除。

当前代码 `backend/app/services/native_heading_repair.py:979` 的 `_candidate_overlaps_table` 同时要求几何覆盖和 `candidate_text in normalize_heading_text(block.text)`；l/1 差异使本应成立的表格归属保护失效。`:955` 的同物理文字保护要求整块等长，不能用一个单行候选去匹配包含大量文字的整表块。`:898` 随后创建正文可见的新块。

因此，修改条款相似度阈值不能根治。应在同侧、同物理区域中确认 native 行归属现有表格，支持行级关联和受约束的混淆字对应；不能全局将合同中的 1、l、I 视作相等。

### 2. D015 / D016：跨页表格结构与内容观察混为一谈

D015 的观察记录明确是 `COMPARE_UNOBSERVED / FIELD_ELEMENT_MISSING`，两侧逻辑表尺寸 11×8 与 10×8。表格诊断中原文逻辑表甚至把人员表、培训表及其他表头纳入同一集合，并标记 `severe_conflict`、geometry confidence 0.2。所谓数字 7 的高亮框高度仅约 1.5 PDF 点，不能支持可靠字符读数。

D016 的直接证据更清楚：原文 `p28_ppocrv5_b3` 是 ocr_line，文本就是 4；对比文同名块是 table，文本也为 4。两侧逻辑表分别 11×8、12×8，最终原文 cell 为 null。诊断 `cross_representation_equivalence` 和 `continuation_content_matches` 均为空。

当前 `table_compare/diff_builder.py:1150` 附近将缺少 cell 映射成 UNOBSERVED；`field_observation.py:73` 正确返回 NEEDS_REVIEW，并没有确认真实增删。但生成结果仍带 ADD/DELETE，事件计数也保留。因此这里应区分两件事：**生成了内容错误的候选**，以及**候选仍进入差异总数**。不能说系统完全没有风险提示；D015/D016 已标注需要复核。

修复应先重建可靠的续表关系、检查原页面内非 table 块的同位置值，再决定是否存在增删。仅过滤全部单字符数字会漏掉真实数值修改。

### 3. D011 / D044 / D048：同一内容被不同模块拥有

封面 IR 中原文 `光功率预测系统设备` 为 doc_title；保存的 OC001 从“技术协议”开始，未包含买方和卖方。NC001 却从“光功率预测系统设备”开始，包含买卖方，不含设计方。因此算法实际比较的不是两张完整封面，而是分流后不对称的残余文本。OC001、NC001 的段落合并置信度均为 0.55，最后成为 DELETE 与 ADD。

目录 D011 的两侧 IR 都保留了“技术协议通用部分”，原文为半角括号，对比文为全角括号；原图页码均为 2。最终仅原文合成带点引导线的“封面额外文本”。能确认的是目录归属/配对失败；尚未通过逐阶段执行定位究竟是哪次点线合并或封面残余提取产生不对称，不把某一个正则判为唯一原因。

应建立封面、目录、签章、正文之间一致的块归属，并在发出单侧增删前查询对侧完整页面的对应证据。目录需按标题与目标页码配对，点线作为版式处理。

### 4. D019 / D023 / D032：有视觉定位，不代表语义正确

- **D019** 把对比第 54 页设计方区域圆章标为“甲方”。任务记录 `PAGE_CENTER_FALLBACK`、confidence 0.35。当前 `signing_region/visual_recall.py:711` 在缺少已识别角色锚点时，按页面左右硬选甲/乙；不适合设计方、买方、卖方纵向排列的签署页。应优先使用明确区域角色，证据不足时保留 unknown。
- **D023** 新增设计方公司这一事实成立；原图印刷名称为“中誉设计有限公司”，保存文字却是“中设限有限公司”。这是印章覆盖下的 OCR 漏字，不是公司真的叫该名称。
- **D032** 把设计方联系人保存成“中”。其 evidence bbox `[187.45,229.97,203.45,253.97]` 落在圆章底部红色“中”字附近，真实手写联系人位于左侧。它把章文字当作字段值。结果同时是 `content_recognition_status=CONFIRMED`、reason `SINGLE_SOURCE`，尽管 overall quality 为 NEEDS_REVIEW。

`signing_region/extractor.py:1323` 附近将单一候选值默认认定 CONFIRMED；额外单源限制仅覆盖签名字段与 date，未涵盖 contact。本例中“定位到了一个字”被误当成“定位到了联系人值”。需先排除章文字污染、建立值与标签/笔迹区域关联，再决定是否确认内容；填入行为与姓名可读性应分别给状态。

3. **空字段标签变化。** D026/D028/D031 的地址、D029/D033 的邮箱标签原图确实不再存在；D030/D035 的“代表（签字）”标签确实出现。它们属于模板文字变化，不能描述成“删除已填地址”或“已经签了名”。

另一个结构问题：通用页面对齐把原文 55 标为 DELETED、对比 54 标为 UNCERTAIN，而签章比较已用原文 55 对比 54。说明页级与区域级对应关系未统一，应修正导航/证据关联，不能只靠相同页码比较。
