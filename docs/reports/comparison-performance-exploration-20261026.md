# 合同比对性能提升空间分析

当前仍有明确的提速空间，长合同最值得优化的是文档解析、页面对齐和最终视觉核验。已有部分优化生效，但串行 OCR、反复建立连接、重复核验与重复渲染仍在消耗时间。本轮已通过隔离实验验证三类收益，没有修改应用代码、生产配置或已有任务。

按这 7 次任务的耗时加权，解析占 **59.9%**，最终汇总及视觉检查占 **11.5%**，条款匹配占 **8.9%**，页面对齐占 **3.9%**。其他阶段合计约 15.8%。短合同主要受解析影响；长合同还会放大对齐、匹配和图像检查的开销。

7 次任务的队列等待均小于 1 毫秒，执行状态记录与流水线计时只相差约 5–28 毫秒。因此这些样本的慢主要发生在处理流程内，增加任务 worker 不能解决其单任务耗时。该样本没有覆盖高并发排队场景。

共读取了 43 条任务记录，其中存在大量同一合同的重复调试记录。这里没有把混合日期、不同代码状态的 43 次任务合成一个产品 P50 或 P95。以上也不包含上传、浏览器加载和 PDF 首次绘制。

## 本轮实验证明的收益

实测使用正在运行的后端对应的 `backend/.venv/bin/python`：Python 3.13.5、PyMuPDF 1.28.0、OpenCV 5.0.0.93、RapidFuzz 3.14.5。以当前未提交工作区为基准，保存了应用源码 SHA256、输入 PDF SHA256 和非敏感配置。实验结束时再次检查，应用源码没有发生变化。

随州和定边完整流程的隔离重跑分别约 **118.08 秒、55.97 秒**，与现有任务的耗时结构一致。隔离重跑额外保存阶段输入，因此不把它和已有任务的几秒差值当作性能退化。

下面的组件比较均为三轮中位数，基线与候选交替执行。

| 实验 | 基线 | 候选 | 变化 | 一致性验证 |
| --- | ---: | ---: | ---: | --- |

## 文档解析的主要机会

当前双文档解析已经并行，Layout 的进程级并发上限为 4。新的机会在 OCR 调度与连接生命周期。

`ContractExtractionV3.extract` 保留全文件语义处理：先完成 Layout，再执行覆盖分析与 OCR，然后识别表格。完全扫描页可提前提交全页 OCR，但 OCR executor 只有 **1 个线程**；MIXED 页在覆盖分析后，逐页逐区域同步请求。随州比对侧的 53 页全部被实际路由为 MIXED，产生 **106 次 OCR 请求**，不能仅因文件名含“扫描件”就把它当作 SCANNED 路径。

随州复跑中，OCR 请求方法累计约 **37.66 秒**，MIXED 页识别循环约 **41.01 秒**；比对侧 OCR 在 Layout 完成后才开始，形成了显著的串行关键路径。定边比对侧是 40 个 SCANNED 页，已经与 Layout 重叠，但单线程 OCR 仍需逐个处理；其解析阶段约 30.52 秒。

`SelectiveOCRRouter._request` 与 `PPDocLayoutV3Client.predict_page` 在默认调用下，每个请求都创建并关闭一个 `httpx.Client`。建议先让连接属于一次文档或任务的生命周期，再为 OCR 请求建立有上限的共享调度。在双文档、双任务同时执行时，总请求数应受同一个预算约束，不能让每层各自开 4 路导致并发相乘。

本轮使用随州解析时真实捕获的 8 个区域请求体，对原服务进行 3 轮、4 种方式的对照，共验证 96 个正式响应。比较覆盖文字、坐标、置信度及归一化 OCR 其他字段，全部一致。这证明连接复用与小并发值得继续做整份合同验证；没有修改 OCR 模型、DPI、识别阈值或区域覆盖策略。

Layout 也存在传输和客户端开销：随州 106 次 Layout 请求共上传约 **93.34 MiB** JSON 请求体；HTTP wall 累计 60.44 秒，响应自报的 inference 累计 6.56 秒、total 累计 9.84 秒、queue 累计 1.00 秒。并行请求时间会重叠，这些累计值不能当作阶段 wall，也不能把差额全部叫作网络耗时，但足以说明当前不能只从 GPU 推理速度解释解析耗时。OCR 服务没有提供同等可用的分项时间。

不建议先降低图像分辨率、跳过 Layout、裁掉正文或省略签章检查。这些会影响输入与业务覆盖，而本轮已经找到不改变请求内容的优化方向。

## 页面对齐可以显著减少无效计算

当前页面对齐仍遍历动态规划状态。随州现有记录中，文本相似度缓存 miss 达 **525,757 次**；缓存存在并不代表无需再减少计算。

实验先用“顺序一对一匹配加尾部缺页”构造一个合法路径的代价上界，再为未处理页数设置保守下界：每消耗一页至少付出 0.025。当前 match 最小代价 0.05，消耗两页；group 最小代价 0.22，消耗三页；gap 最小代价 0.42，消耗一页。只跳过下界已严格超过合法路径上界的状态，并保留浮点比较余量。

这没有强制页面按相同页码对应，没有删除插页、删页或拆并页能力，也没有改变评分、转移顺序及回溯规则。两份完整长合同的三轮结果相同；另外 60 组基于真实页面构造的插页、删除、重复、重排、拆页、并页、空文档及不变输入的差分实验，结果全部相同。

这是目前最适合先实现的算法优化：改动范围集中，长合同收益稳定，且可直接比较完整 `PageAlignmentEntry`。上线前仍应覆盖完整 Golden 合同与最终差异结果，不能只验页映射。

## 汇总阶段的视觉重复工作

`SummaryStage` 除统计之外还执行全页矩阵图形检查、透印核验、页脚对象归属、观察项协调和事件生成。随州 profiler 的主要数据为：

| 操作 | 观测 |
| --- | --- |
| 矩阵图形全页扫描 | 约 5.35 s |
| 透印协调 `reconcile_impressions` | 约 12.90 s |
| `cv2.matchTemplate` | 20,880 次，约 10.81 s |
| `ImpressionVerifier.render` 实际渲染 | 439 次，约 5.94 s |
| 页脚对象协调 | 约 3.20 s |
| 事件快照构建 | 约 0.085 s |

这些操作有父子调用关系，不应逐行相加。数据说明主要开销是图像检查，优化事件 JSON 或统计循环不会解决这份合同的主要问题。

当前 `ImpressionVerifier.render` 是按 verifier 实例缓存、最多 8 页，各阶段又重新创建 verifier 并清空缓存。同一张 PDF 页面及同一证据区域可能反复计算。实验按任务内文件身份、页码、完整 bbox、seal 与递归检查选项复用核验结果，读取缓存时深复制结果，避免调用者修改缓存；每轮命中 **103 次**。进一步共享相同像素参数的页面渲染后，视觉 verifier 只需渲染 **53 次**，缓存命中 **1,183 次**。

渲染候选设定 256 MiB 上限，实际保留约 **171 MiB** 图片；相比原来的小缓存，需要更多内存。整任务现有通用渲染缓存仅 64 MiB，随州记录为 216 次 miss、1 次 hit，且它不包含这部分独立 verifier 缓存。不能只扩大现有缓存就期待自动获得上述收益，必须接通相同图像规格的复用。

解析器的 `images` 列表仍保留整份文档的图像，虽然 Layout pending 队列有界，图像总体并未随队列一起释放。两份长合同复跑的进程阶段采样 RSS 约 1,667–1,749 MiB；这是进程总量，不是任务增量或精确峰值。因此视觉缓存和 OCR 并发落地时，需要同时验证内存与两个并发任务，避免把单任务加速换成并发时的内存压力。

仓库已有 `MatrixScanJob`，但当前 `PipelineContext`、`PageAlignmentStage` 和 `SummaryStage` 没有接入它，现在线上流程仍在 Summary 内同步等待矩阵扫描。将这一独立检查与中间阶段重叠，有望隐藏随州约 5 秒、定边约 2 秒的等待；这是未整合验证的机会，不能再叠加算入已实测的汇总优化收益。

## 条款匹配的判断

定边复跑匹配约 **10.66 秒**，其中重排批次 wall 约 **5.40 秒**、embedding 批次 wall 约 **1.54 秒**、规则候选评分约 **2.49 秒**。现有精确匹配跳过重排、特征缓存和模型请求并发已经开启，不应作为新的优化建议重复计算。

复测历史 `score_cutoff` 候选时，使用定边捕获的 HTTP 响应严格回放，所有请求命中缓存、没有 HTTP 失败，三轮完整 ClausePair 相同。但匹配阶段中位数只有 **3.821 → 3.763 秒**，样本区间明显重叠，候选单轮还出现变慢。当前没有足够收益证据，不建议优先推广，也不能沿用九月实验的收益数字。

随州还有一个会污染基线的实际问题：重排服务返回 **2048 token 上限**错误，2 个不同请求各被再次尝试，共 4 次 HTTP 400。失败会把共享 reranker 的 `enabled` 置为 False。182 个需要重排的候选组最终只实际尝试了 89 组，余下请求会因降级不再正常执行。因此随州条款匹配比定边快，不代表它在更大输入上扩展得更好。

对确定性的长度错误应停止无意义重试，并单独解决长文本如何在保留业务信息的前提下重排。修复降级可能让重排耗时上升，这是恢复计算覆盖，不能作为性能退化拒绝修复。也不建议直接截断正文或调低 top-k 来制造提速。

## 建议实施顺序与收益口径

1. **页面对齐精确剪枝。** 两份长合同的组件收益与输出一致性已经明确，优先落地并跑完整业务回归。
2. **OCR 连接复用与有界并发。** 请求样本收益明确，覆盖面最大；先验证完整 MIXED 与 SCANNED 文件，再验证两个任务同时运行。
3. **任务级视觉核验和图像复用。** 对页脚印迹多的长合同有效；把缓存内存预算作为实现的一部分。若内存不允许扩大，单独复用区域核验结果也已有约 2 秒收益。
4. **矩阵扫描与中间计算重叠。** 已有独立模块，但尚未接入，需验证异常、取消和最终输出顺序。

仅页面对齐加视觉复用，随州组件节省合计约 **12.3 秒**，相当于其现有 113.2 秒流水线的约 **11%**。这是保持其他阶段不变的加总估计，不是组合方案的端到端实测。定边仅页面对齐对应约 **3.5 秒、6%**。OCR 调度改善可能继续带来更大收益，但完整文档内的 Layout、OCR、表格与双文件重叠关系必须通过重跑量化，不能把请求批次的 50.2% 直接乘到总耗时上。

重复标准合同的持久解析缓存也可能减少后续任务耗时，但本轮没有验证缓存命中率、模型版本一致性和完整提取产物复用，不给出收益数字。首先应完成上面已有证据支持的优化。

性能观测也需要补齐：`task_observability.py` 定义了任务和阶段观测上下文，但没有接入当前流水线。已有 `benchmark_support.build_service` 仍向 `CompareService` 传入已移除的 `structured_extractor` 参数。本轮使用独立探针绕开这一接口失配，没有把旧脚本的存在当作当前基准可直接运行的证明。
