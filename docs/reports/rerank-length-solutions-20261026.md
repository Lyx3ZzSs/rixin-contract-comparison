# 长文本重排超限的解决方案

建议分两步处理：先把长度错误限制在具体候选对内，停止重复请求和跨组降级；再验证把现有模型服务的上下文上限提高到 8192，并用准确的 token 预算替代现有 1600 字符截断。分块可作为无法调整服务时的备选，但其分数不能未经校准直接替代完整条款的重排分数。

本轮使用当前工作区、现有服务和随州真实候选进行隔离实验。没有修改应用代码、模型服务配置或已有任务。

## 已确认的根因

实际服务返回版本为 **vLLM 0.25.1**，`/v1/models` 返回 `bge-reranker-v2-m3`、`max_model_len=2048`。

客户端 `RerankMatcher._rerank_text` 已将每侧的 `title + text` 截取为前 **1600 个字符**。但模型限制针对每个 **query 与 document 合并后的 token 序列**，不是单侧字符数，也不是整批 30 个 document 的 token 总和。XLM-R 的这一文本对格式另需 4 个特殊 token，本轮用服务 `/tokenize` 计数，并与实际 `/rerank` 返回的 usage 核对。

随州全部 182 个待重排候选组、5,460 个候选对中，实际只有 3 对超过当前上限：

| 原条款 | 比对条款 | 合并 token 数 | 所在组的合法候选数 |
| --- | --- | ---: | ---: |
| OC125 | NC141 | 2078 | 29 / 30 |
| OC137 | NC141 | 2249 | 28 / 30 |
| OC137 | NC129 | 2077 | 28 / 30 |

将超限对单独发送仍返回 HTTP 400，证明减小批次或降低 top-k 不能根治单个文本对超长。剔除这 3 对后，两组剩余 29、28 对全部成功，单个批次返回的总 usage 分别达到 29,799 和 33,341 token，也再次说明 2048 是每对的限制。

错误被客户端放大了两个层级：

1. 一个 document 超限，会让同组其他合法 document 一起拿不到重排结果。
2. `score_candidates` 重试同样的 400 后，将共享的 `self.enabled` 设为 False，随后尚未开始的其他组直接返回不可用。

最小复现只需要“一个超限候选对，随后一个正常候选对”：前者请求两次；后者请求零次；正常候选也失去评分。对应脚本的断言能稳定报出这一错误。

并发进一步导致结果不稳定。相同输入的三次当前实现重跑，实际尝试的组数为 **90、90、89**；第三次 `OC145 → NC149` 的 `rerank_available` 从 1 变为 0，重排分数从 99.99 变为 0。虽然这次最终条款对应关系没有改变，但模型覆盖范围和诊断结果已受线程执行时序影响。

## 当前部署上限与模型能力不同

官方模型配置的 `max_position_embeddings` 为 8194，tokenizer 配置的 `model_max_length` 为 **8192**。因此当前 2048 是服务使用的上下文限制，而非该模型官方配置只有 2048。扩大服务上限仍需在实际 GPU 上验证内存、延迟和并发。来源：[官方模型配置](https://huggingface.co/BAAI/bge-reranker-v2-m3/raw/main/config.json)、[官方 tokenizer 配置](https://huggingface.co/BAAI/bge-reranker-v2-m3/raw/main/tokenizer_config.json)。

服务端实际 OpenAPI 及对应版本源码支持 `truncate_prompt_tokens`、`truncation_side`、`max_tokens_per_query` 和 `max_tokens_per_doc`。这些字段用于截断输入，不能扩大服务端模型上限。来源：[vLLM 0.25.1 scoring 协议](https://github.com/vllm-project/vllm/blob/v0.25.1/vllm/entrypoints/pooling/scoring/protocol.py)。

准确计数得到的容量需求如下，范围仅为本次随州候选：

| 输入方式 | 超过 2048 的组 / 对 | 最大文本对 | 4096 是否足够 | 8192 是否足够 |
| --- | ---: | ---: | --- | --- |
| 保留当前 1600 字符截断 | 2 / 3 | 2249 token | 是 | 是 |
| 保留完整标题及正文 | 21 / 50 | 5240 token | 否，有 1 组仍超限 | 是 |

当前字符截断实际影响了 1 个原条款和 1 个比对条款。最长完整对是 `OC137 → NC141`，两侧分别为 3709、3703 字符，对应正文及标题 token 2621、2615，合并为 5240。提高上限后如果仍保留 `[:1600]`，只能消除当前 HTTP 错误，无法恢复这些被提前裁掉的内容。

## 方案对比

| 方案 | 能解决什么 | 本轮验证 | 结论 |
| --- | --- | --- | --- |
| 精确计数并隔离超限对 | 恢复同组合法候选和后续组，消除跨组失败扩散 | 182 组全部执行，5457 对正常评分，3 对明确降级 | 首先实施 |
| 服务上限提高到 4096 | 容纳目前已截到 1600 字符的请求 | 当前最大 2249，容量足够；未改服务配置验证推理 | 可作短期过渡 |
| 服务上限提高到 8192，取消字符截断 | 让本次所有完整条款对一次评分 | 完整最大 5240；官方模型配置支持该长度范围 | 推荐的目标方案，需服务实测及质量回归 |
| 服务端直接截断到 2048 | 消除请求错误 | 3 个失败样本均可成功，但方向改变评分显著 | 不作为默认修复 |
| 超限对使用重叠 token 窗口 | 在现有服务上覆盖更多内容 | 当前 3 对成功补足；最长完整对也可分块运行 | 保留为备选，聚合方式需校准 |

## 优先修复失败隔离

影子实现预先计算每个候选对的长度，同一个原条款下仅把合法 document 发给服务，再按原索引还原结果。超过预算的候选仍保留在候选集中，由规则及其他现有信号评分；其重排应标记为不可用，不能把“未评分”伪装成“模型评分为零”。

三轮结果为：

- 182 个组全部执行，5,457 个候选对有正常重排分数，3 个候选对因长度明确降级。
- 没有发生长度 HTTP 400，也没有因此关闭后续组。
- 三轮完整 ClausePair 输出相同，与此前任务的条款对应关系一致。
- 恢复了后续评分，93 个选中 ClausePair 的完整评分或诊断字段与此前降级基线不同；因此不能把“对应关系相同”称为整个业务结果等价。

正式实现应将静态配置 `enabled` 和运行时失败状态分开，不能让单个输入错误修改共享开关。错误策略建议为：

| 错误类型 | 处理方式 |
| --- | --- |
| 已识别的长度 400 | 不原样重试；精确定位到超限候选对，走长文本路径或明确降级 |
| 其他请求参数错误 | 记录原因、保留同任务其他合法请求的执行机会；不能按长度错误猜测处理 |
| 超时、429、可恢复的 5xx | 有界重试及退避，失败范围限于相应请求；持续服务故障另行记录 |
| 鉴权或配置错误 | 显式暴露任务级模型不可用原因，避免静默表现为正常完成重排 |

`_apply_rerank` 当前还会丢弃不可用评分携带的原因。落地时需把 `context_length_exceeded`、`upstream_error` 等状态传到候选诊断，并记录计划组数、实际尝试组数、成功候选对数、超限对数、重试次数和覆盖率；否则缺失评分仍难以解释。

预算应使用与服务模型一致的 tokenizer 和版本，按任务缓存每段文本的 token 数。此次用远端 `/tokenize` 做探索，不建议生产代码为每个候选对重复请求 tokenizer。4 个特殊 token 的开销也应绑定实际 tokenizer 格式，不作为所有模型通用常数。

## 为什么不直接打开截断

对 3 个真实失败候选，服务端截断都返回成功，但分数变化明显：

| 候选对 | 保留开头的整体截断 | 保留结尾的整体截断 | 保留 query，仅缩短 document |
| --- | ---: | ---: | ---: |
| OC125 → NC141 | 0.8896 | 0.0315 | 0.8669 |
| OC137 → NC141 | 0.5383 | 0.0359 | 0.4917 |
| OC137 → NC129 | 0.3574 | 0.0214 | 0.3263 |

此处是服务原始 0–1 分数；客户端随后会转换为百分制。这证明截断方向实际改变了模型看到的内容和评分。即使“保留 query”更符合检索场景，也会丢失 document 尾部，不能保证保留合同尾部的金额、期限、否定条件或责任范围。

这些数值没有完整 8192 推理分数作为真值，不能仅凭其中某个分数较高就判定某种截断更准确。

## 分块方案的效果与边界

对当前已经经过字符截断的 3 个超限对，保持 query 不变，根据剩余 token 预算把 document 分成两个窗口，重叠 128 token，并对重新编码后的长度再次校验。所有窗口均可由当前服务处理。

将这一候选接入隔离的完整条款匹配后，182 组、5,460 个候选对全部获得评分，实际推理 5,463 个窗口对，三轮条款对应关系仍与此前任务一致，三轮 ClausePair 输出也相同。此实验使用窗口最大分数，**仅证明可运行及这个样本的对应关系未变，不证明该聚合具有普遍正确性**。

它还没有解决已有 1600 字符裁剪。针对完整的 `OC137 → NC141`，query 自身就有 2621 token，必须同时拆两侧。采用约 1000 token 窗口、128 token 重叠，可覆盖原始两侧全部 token，需要 3 × 3＝9 个窗口对。本轮实测：

- 共处理 17,292 token；3 个评分请求约 0.243 秒，不含分词和分块准备。
- 全部窗口最大分为 **0.8541**。
- 按原 query 覆盖长度加权的最佳窗口分为 **0.6131**。
- 反方向加权结果为 **0.5631**；取双向较小值同样为 **0.5631**。

“取最大值”容易让一个公共段落代表整个条款；简单平均又可能惩罚合理的拆并关系。覆盖加权也仍然改变原有评分定义，并丢失跨窗口交互。因此若采用分块，需要明确窗口边界、覆盖率、聚合函数、排序稳定性和新阈值的验证，复杂度高于直接利用现有模型的完整上下文。

## 对性能基线的实际影响

为保持可比性，以下各组三轮都使用相同冻结的 embedding 响应、真实重排服务及同一份条款输入；分词预处理不计入测量。不同方案按组运行，并非交替实验，微小时间差不作性能结论。

| 实现 | 匹配耗时中位数 | 实际组数 | 评分覆盖 |
| --- | ---: | ---: | --- |
| 当前实现，发生全局降级 | 4.627 s | 90 / 90 / 89 | 超限失败后大量组不再执行 |
| 隔离 3 个超限对 | 6.951 s | 每轮 182 | 5457 / 5460 对 |
| 隔离并对超限对分块 | 7.044 s | 每轮 182 | 5460 / 5460 对 |

恢复正常重排后，本样本多用约 **2.3 秒**，同时消除了大量缺失评分和并发时序造成的不稳定。这部分是恢复工作覆盖的成本，应建立新性能基线，不能继续把错误降级后的较短耗时作为优化目标。

## 推荐落地顺序

**第一步，客户端错误隔离与诊断。** 保留合法候选评分，长度错误不重试、不污染其他组。为“坏候选之后的好候选仍被执行”、同组混合长短候选、并发顺序变化以及不可用原因保留建立回归检查。

**第二步，验证现有模型的 8192 服务能力。** 在受控实例或维护窗口调整既有部署的 `--max-model-len`，核对服务实际返回的上限、长输入批处理预算、GPU 内存和并发延迟。若只能先启用 4096，应明确它只兼容现有字符裁剪后的请求，仍不是完整长条款方案。本轮没有修改部署或声称已经跑通 8192 推理。

**第三步，token 预算替代字符裁剪。** 在确认服务容量后，对预算内的完整 `title + text` 直接重排，移除 `[:1600]`。未来仍可能出现超出 8192 的输入，必须保留明确的超限状态及长文本备选路径。

**第四步，业务与性能验收。** 对正常短文本保持现有匹配与审查语义；重点覆盖真实长条款及尾部金额、日期、否定词、责任范围变化。跑完整 Golden 和最终差异、证据、观察项、事件快照检查，再建立“全部应重排候选都得到评分或明确记录降级”的端到端基线。

## 复现与证据

原始证据位于 `output/analysis/rerank-length-exploration-20261026/`，包含服务版本、模型元数据、OpenAPI、完整长度分布、最小失败请求、三种匹配路径输出与分块结果。服务凭证没有写入实验文件。

复现当前故障的命令如下，**预期退出码为 1**，断言信息为 `BUG REPRODUCED: deterministic 400 retried and unrelated good pair disabled`：

```bash
backend/.venv/bin/python output/analysis/rerank-length-exploration-20261026/survey.py
```

影子方案重跑：

```bash
backend/.venv/bin/python output/analysis/rerank-length-exploration-20261026/guarded_matching.py isolate
backend/.venv/bin/python output/analysis/rerank-length-exploration-20261026/guarded_matching.py windows
```

这两个方案保留当前字符裁剪，用于验证错误隔离和窗口策略。完整正文的双侧分块实验入口为 `full_window.py`，截断参数对照入口为 `variants.py`。8192 原文推理、全量业务回归和部署资源验证尚未执行。
