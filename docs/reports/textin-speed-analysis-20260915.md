# TextIn 与本项目比对耗时差异分析

日期：2026-09-15。范围：读取当前任务数据库、已有 TextIn 原始响应和官方 API 文档，检查当前代码，并执行无外部调用的 PDF 文字层读取与页面对齐组件探针。未重新提交 TextIn、OCR、embedding、rerank 任务，未修改业务代码或保存任务。

## 结论

差距来自两部分：本项目的文档识别路径更重，识别后的页面对齐与匹配也存在可验证的额外开销。不能归结为 TextIn 用 GPU、本项目没并发，或单纯认为字符串 diff 算法慢。

尤其是 55＋54 页样本：本地最新任务 206.18 秒中，文档解析为 94.34 秒，其余流程为 111.83 秒。即使把解析压到 TextIn 的 20.11 秒，其余不变仍需约 131.94 秒。OCR 加速本身不足以达到 TextIn 的现有记录。

## 1. 计时口径与样本

| 样本 | 本地解析 | 本地解析后全部阶段 | 本地流水线总时长 | TextIn parse_duration | TextIn compare_duration | TextIn 两项之和 |
|---|---:|---:|---:|---:|---:|---:|
| 22＋22 页，8eb0a225 | 26.454 s | 25.100 s | 51.554 s | 7.790 s | 0.960 s | 8.750 s |
| 55＋54 页，437aa215 | 87.598 s | 104.219 s | 191.817 s | 20.107 s | 1.384 s | 21.491 s |
| 同一对 55＋54 页 PDF 的最新本地任务 ee13fef9 | 94.344 s | 111.833 s | 206.178 s | 沿用上述同输入外部结果 | 沿用上述同输入外部结果 | 21.491 s |

TextIn 官方将两项字段定义为解析耗时和比对耗时，单位毫秒，但没有在该文档中披露完整埋点边界、两份文档的内部调度、缓存命中及设备配置。因此这里只比较已报告的阶段时间，不能把约 6 倍、9–10 倍解释为同硬件、同模式的纯算法差距或完整用户等待时间差距。

本地流水线包括外部 OCR HTTP 等待、文档准备、页面对齐、表格/签章处理、模型匹配、质量检查、图形扫描和事件汇总；TextIn 的 compare_duration 不能与本地某个同名阶段机械一一对应。

来源：[TextIn 获取差异信息](https://www.textin.com/document/doc-compare-diff-info)。本地时间和外部请求参数的摘录见 [timing-evidence.json](../../output/analysis/textin-speed-20260915/timing-evidence.json)。

## 2. 解析路径不同，是有证据的首要差别

两次 TextIn 请求均为 `use_pdf_parser="true"`。官方说明该参数开启 PDF 解析，设为 false 则使用 OCR 识别；水印擦除关闭，所有印章等保留参数见原始请求。

本项目实际运行 `ppstructure_ocr_hybrid`，对两份文件各调用 PP-OCRv5 和 PP-Structure，然后融合。实际记录与当前选定配置均显示：文档间并行已开启、两个组件间并行已开启，native fast path 关闭。不能用配置类的默认 false 推断实际没有并发。

### 文件的真实文字层

本轮直接用 PyMuPDF 读取同输入 PDF 的文字层，哈希与 TextIn 输入记录一致：

| 输入 | 总页数 | 原生文字不少于 80 字的页数 | 提取字符数 | 单次只读文字提取 |
|---|---:|---:|---:|---:|
| 原文 | 55 | 52 | 35,980 | 0.053 s |
| 对比文 | 54 | 1 | 149 | 0.055 s |

这解释了原文有机会直接利用文字层、对比文必须大量依赖图像识别。但这不是完整结构化解析耗时，也不证明 TextIn 每一页的具体路由。文字层读取不提供完整表格结构、手写签名和印章识别。

### 本地耗时落在远端调用

ee13fef9 保存的 HTTP 用时：

| 输入 | PP-OCRv5 HTTP | PP-Structure HTTP | 整侧提取 |
|---|---:|---:|---:|
| 原文 | 30.84 s | 51.28 s | 51.93 s |
| 对比文 | 57.10 s | 92.83 s | 93.56 s |

并行后的解析总阶段为 94.34 秒，主要等待最慢的对比文 PP-Structure。组件内 JSON 解码、结果转换和写文件远小于 HTTP 时长。HTTP 时间包含传输、服务端排队和推理，没有服务端内部指标就不能再拆出各自贡献。

这是四次整文件识别请求，融合两种模型输出确实增加了计算和传输工作。无法从现有记录断言 TextIn 自身只跑一个模型，但可以确定两家未使用相同的提取模式。已有 native 快路径要求两份文件都通过检查，并会拒绝表格、嵌入图片等复杂特征；简单把开关改成 enabled，并不能解决这组混合文档。

代码：[混合提取](../../backend/app/services/extractors/ppstructure_ocr_hybrid.py)、[快路径选择](../../backend/app/services/pipeline_stages.py)、[快路径资格检查](../../backend/app/services/native_fast_path.py)。官方参数：[创建比对任务](https://www.textin.com/document/legacy/doc-compare-create)。

## 3. 页面对齐存在实测可消除的重复计算

完整任务保存阶段为 44.13–46.89 秒。`PageSequenceAligner` 对 n×m 个页面状态计算一对一、两页合一、一页拆二的匹配；支持判断又重复计算部分相同相似度。每次相似度还包括全文 SequenceMatcher、重新生成 n-gram、最多 12×12 个锚点比较以及布局集合计算。

因此 55×54=2,970 并不是实际字符串比较次数。它是一个包含大量重复字符串比较的动态规划流程。页面对齐模块没有调用 OCR、embedding 或 rerank 服务；这部分开销可从本地算法着手。

本轮以最新任务保存的原始融合文档执行组件探针，只在第二次调用中给 `_similarity` 增加单次运行缓存：

| 指标 | 结果 |
|---|---:|
| 原算法时间 | 46.595 s |
| 相似度调用数 | 26,457 |
| 不重复的有向参数对 | 14,685 |
| 复用计算次数 | 11,772 |
| 加缓存后的时间 | 26.613 s |
| 时间减少 | 19.983 s，约 42.9% |
| 两次页面对齐输出 | 完全一致 |

这证明存在可避免的重复工作。探针使用的是完整任务清洗、准备阶段之前保存的融合文档，不是完整流水线输入状态回放；只验证此组件同输入输出一致，不能宣称整体上线可稳定减少 20 秒。缓存不交换左右参数，因为 SequenceMatcher 等计算不能在未经验证时当作对称函数。

复现：在项目根目录执行 `.venv/bin/python output/analysis/textin-speed-20260915/probe_alignment.py`。证据：[alignment-probe.json](../../output/analysis/textin-speed-20260915/alignment-probe.json)。

## 4. 条款匹配工作量远大于一次文本 diff

最新 55＋54 页任务匹配阶段 27.83 秒，其中候选生成 27.63 秒，包含规则评分和语义模型调用：

- 原文 367 条、对比文 363 条，生成 37,903 个候选对，约为完整笛卡尔积的 28.5%。
- 730 个输入文本，23 次 embedding HTTP 请求，实际并发 3。
- 367 组 rerank HTTP 请求，11,010 个候选文档，即每组 30 个；实际并发 8。
- 全局分配只用 0.063 秒，保存匹配诊断约 0.079 秒。

`_rerank_groups` 按原文条款分组后取 top-k，没有在这一层仅选择歧义条款。页面对齐结果也是候选来源之一，而非严格限制搜索范围；位置窗口为相对位置 ±15%，长文档上自然产生较多候选。候选评分还包含正文、编号、路径、邻居、业务字段和对齐诊断。

因此当前慢点包括宽候选搜索、多项评分和模型请求，不能把 27 秒全部归给 rerank。记录中的 rerank 请求累计 54.96 秒是并发请求时长之和，不是流水线新增 54.96 秒；它也包含在候选生成阶段内，不能再次相加。

对照 22＋22 页任务：候选对 2,418，rerank 73 组，匹配 2.89 秒。随着条款数增加，候选和评分成本增长明显。这些记录不能反推出 TextIn 没使用语义模型，只能说明本项目的工作量与 TextIn 的未公开流程不能按名称视为相同。

代码：[候选召回与重排](../../backend/app/services/matching/candidate_recall.py)、[多项评分](../../backend/app/services/matching/candidate_scoring.py)。

## 5. 其他重处理与计时名称

最新长合同剩余主要阶段：文档准备 11.14 秒，表格等差异识别 6.55 秒，签章识别 8.06 秒，汇总统计 10.51 秒。

“汇总统计”并非只是加减数字。`SummaryStage` 会调用 `MatrixGraphicComparator`，遍历两份 PDF 的每一页、渲染灰度图并查找二维码类图形，然后做差异归并和事件快照。该组件缓存仅在自身调用期间使用。10.51 秒是整个汇总阶段，没有更细计时前不能将其全部归因于渲染或二维码检测。

22 页样本的签章阶段反而有 13.84 秒，说明内容、签章分布和识别难度影响显著，页数不是唯一变量。

## 6. 哪些 TextIn 原因尚不能确定

| 说法 | 证据边界 |
|---|---|
| TextIn 启用 PDF 解析，能利用电子档文字层 | 请求和官方参数已确认；逐页实际路由未披露 |
| TextIn 本样本解析和比对字段更短 | 原始响应已确认；不等于同口径端到端基准 |
| TextIn GPU 更多、批处理更强、模型常驻 | 可能，但没有本次部署与推理日志证明 |
| TextIn 命中缓存才这么快 | 没有缓存命中记录，不能下结论 |
| TextIn 算法是某种线性算法，或完全不用语义模型 | 内部实现未公开，不能下结论 |
| 本项目更慢所以更准 | 不成立；双方均有原图核实的误报或错配 |

速度与准确率需要独立验收。已有 [437aa215 交叉核查报告](437aa215-textin-verified-analysis.md)记录双方错误；不能以输出条数或处理时间代替质量评价。

## 7. 优化优先级

1. **先消除不改变判定逻辑的重复计算。** 页面相似度缓存、页面特征预计算、锚点比较缓存，按单次任务限制内存；先验证页对应输出及真实删页、拆页、合页样本。
2. **减少不必要的候选评分与重排。** 高置信对应优先锁定，歧义区域再扩搜和调用模型；保留跨页和结构变化回退。需要质量对照，不能直接全关模型。
3. **按页面和区域组合原生解析与 OCR。** 利用可靠文字层，针对扫描、表格、签章等区域保留必要识别；已有全文件双侧准入开关不足，需要更细路由。
4. **继续拆解远端 OCR 和视觉阶段。** 区分上传、排队、推理及渲染/检测；复用适当分辨率的页面图像，在保留真实图形变化的前提下缩小重复扫描。

下一次同口径基准应同时记录客户端提交至结果、各服务内部阶段、缓存状态、实际参数、输入哈希和结果质量。现有证据足以定位本项目优先改进处，但不足以承诺优化后达到 TextIn 的 20 秒级。
